Negócios

Objetivo básico:
- Embora essa tabela se chame "Negócios" ou "Deals", ela é, na realidade, um cadastro de "coisas" que começam e terminam (como processos, oportunidades de venda, projetos, entre outros);
- Todo negócio tem uma situação. Ou ele está em aberto, ou encerrado como ganho ou como perdido (e quando está como perdido, obrigatoriamente tem vinculado a ele um motivo de perda). Apesar dessas nomenclaturas, é possível criar um frontend que manipule os verbos, ou que mesmo oculte, por exemplo, a possibilidade de perder.
- Negócios estão obrigatoriamente vinculados a um funil (sem possibilidades de estarem em dois funis ao mesmo tempo);
- Negócios possuem um campo chamado "cliente" para armazenar a empresa ou pessoa ao qual ele pertence. Se o cliente for uma empresa, eu ainda posso vincular uma pessoa no campo "contato". Por fim, pelo campo "Contatos relacionados", consigo vincular outras empresas e pessoas. Obs.: não é obrigatório um negócio estar vinculado a qualquer cliente.
- Um negócio pode conter negócios vinculados abaixo dele. Isso significa que posso ter um "negócio pai" com vários "negócios filhos". Entretanto, um negócio filho pode ter apenas um negócio pai;
- Um negócio pode se movimentar de um funil para o outro;
- Eu consigo, também, criar automações que geram negócios filhos em outros funis, por exemplo;
- Eu posso criar checklists em determinadas etapas do funil que obrigam o usuário a preencher determinadas informações antes que ele consiga avançar o negócio de etapa;
- Com essas ferramentas, é possível criar processos conectados (incluindo processos multidepartamentais). Exemplo: um negócio avança para a etapa X do funil A e isso gera, por automação, um novo negócio filho no funil B. Configuro um campo no checklist da etapa X do funil A (não preenchível pelo usuário) que, caso esteja vazio, impede o avanço do negócio para a etapa seguinte. Em seguida, quando o usuário finalizar o negócio do funil B, uma automação edita o campo do checklist com um valor qualquer do negócio do funil A, liberando o usuário para avançá-lo para a próxima etapa (ou até avançando automaticamente pela automação). Em resumo, este exemplo mostra um macro processo A com um sub-processo B acontecendo.
- No exemplo acima, seria possível simplesmente movimentar o mesmo negócio do funil A para o funil B, mas isso faz com que eu perca taxas de conversão de cada funil, perca visibilidade do status daquele macro processo em cada funil, e dificulta regras de visualização, caso um time só possa ver coisas do funil A e outro somente do funil B.

Dados:
- A base de negócios se utiliza dos mecanismos de formularios_e_campos do Ploomes. Eu posso ter um formulário por funil. Apesar disso, a lista de campos é uma só para todos os negócios, ou seja, eu posso reutilizar os mesmos campos em funis diferentes, e a lista de negócios é uma só para negócios de todos os funis;
- Para se armazenar diferentes tipos de negócios, é preferível o cadastro de funis diferentes para cada um (exemplo: um funil de vendas, outro funil de assistência técnica). Dessa forma, você consegue criar etapas para cada um, com automações e checklists para cada um de forma mais simples;
- Ainda sim, é possível se utilizar apenas de técnicas de front-end (mas só faça isso caso os métodos nativos não sejam suficientes para casos de uso mais customizados, porque o Ploomes está melhor indexado para filtragem por funil). Exemplo: posso criar um único funil e um campo do tipo "Tipo de negócio". Depois, eu crio apenas uma etapa no funil, e crio um novo campo de opções pré-cadastradas para armazenar o estágio (sendo que, no seu front-end, você pode simular funis diferentes gerando estágios para somente determinadas opções desse campo). À medida que o estágio muda (exibindo de forma condicional no front-end para cada caso de uso), eu posso gerar automações que engatilham somente quando o campo em questão for alterado, e que rodam condicionalmente a partir do que for preenchido no campo. O mesmo para checklists. Posso rodá-los condicionalmente de acordo com o campo preenchido no campo.
- Negócios também usam o sistema de abas_e_tabelas_dinamicas. Ao montar telas, você pode se utilizar disso, ou fazer queries na API direto da forma que preferir. O benefício de se utilizar o sistema de abas é a otimização delas em termos de carregamento e exibição de dados.
- Importante ressaltar que negócios possuem suas regras de visualização definidas em perfis_de_usuario.
- Um negócio pode ter outro negócio vinculado como Negócio origem (um campo). Nesse sentido, um negócio pode ter vários "filhos" e um único "pai";
- Os demais vínculos entre Negócios e outras entidades estão definidos no arquivo (RC) Lista_de_field_paths.txt, que é a fonte canônica de todas as relações entre entidades.

Observação: para todas as entidades que possuem campos dinâmicos, sempre é possível criar um campo do tipo número inteiro e armazenar o ID de um negócio "virtualmente" vinculado, ou seja, um vínculo sem comportamento no Back-end, mas que o front-end pode se utilizar para aparentar vínculo real ao usuário.
